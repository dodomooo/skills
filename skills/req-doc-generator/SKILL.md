# 需求文档生成器

根据用户的原始需求描述和上下文文档，通过强制问题澄清流程，生成标准格式的软件需求文档。

## 工作流程

生成需求文档包含以下步骤：

1. 收集输入并加载上下文
2. **强制问题澄清**（必须完成后才能继续）
3. 生成需求文档

## 步骤 1：收集输入并加载上下文

### 原始需求

用户直接输入的需求描述。可能是简短的一句话，也可能是较详细的描述。

### 上下文文档

上下文分为两层：

**固定上下文** — 产品基础文档，存放于项目 `context/fixed/` 目录：

- 产品说明书、架构文档、术语表等
- 每次生成需求文档时自动加载
- 读取目录下所有支持格式的文件（.docx、.xlsx、.pptx、.pdf、.md、.txt）

**动态上下文** — 本次需求相关的参考资料，存放于项目 `context/dynamic/` 目录：

- 会议纪要、竞品分析、用户反馈等
- 每次需求生成前由用户放入
- 读取目录下所有支持格式的文件
- 加载前先列出目录内容，向用户确认这些文件是否为本次需求的参考资料（避免上次遗留文件污染）

加载顺序：先固定上下文，后动态上下文。动态上下文可补充或覆盖固定上下文中的信息。

### 文档处理

支持的文档格式及处理方式：

- **.md / .txt** — 直接读取文本内容
- **.docx** — 使用 `docx` skill 读取内容
- **.xlsx** — 使用 `xlsx` skill 读取内容
- **.pptx** — 使用 `pptx` skill 读取内容
- **.pdf** — 使用 `pdf` skill 读取内容

读取文档时：

1. 列出 `context/fixed/` 和 `context/dynamic/` 下的所有文件
2. 按格式分类，逐个读取内容
3. 将所有内容整合为结构化的上下文摘要

## 步骤 2：强制问题澄清

**这是必需步骤，不可跳过。** 在生成文档前，必须向用户提出澄清问题并获得回答。

根据原始需求和上下文内容，智能识别以下类型的模糊或缺失信息：

- **目标用户**：需求面向哪些用户角色？
- **业务场景**：具体的使用场景和触发条件？
- **功能边界**：哪些在范围内，哪些明确排除？
- **数据要求**：涉及哪些数据，数据来源？
- **性能指标**：响应时间、并发量等是否有要求？
- **兼容性**：需要支持哪些平台、浏览器、设备？
- **依赖关系**：与哪些现有系统或模块有交互？
- **优先级**：各功能项的优先级排序？
- **验收标准**：如何判定需求已实现？
- **约束条件**：时间、技术、资源等限制？

澄清规则：

- 分析原始需求和上下文后，仅提出**上下文中未明确**的问题
- 问题总数控制在 3-8 个，避免过多打扰用户
- 每个问题附带选项或示例，降低用户回答成本
- 使用 `AskUserQuestion` 工具提问（该工具单次最多 4 个问题，超过时分批提问）
- 收到回答后，判断是否需要追加澄清（最多追加一轮）

## 步骤 3：生成需求文档

完成问题澄清后，按照标准模板生成需求文档。详见 [references/doc-template.md](references/doc-template.md)。

生成规则：

- 输出为 Markdown 格式
- 严格遵循模板结构，不可自行增删章节
- 每个功能需求必须包含：编号、描述、优先级、验收标准
- 非功能需求必须可量化或可验证
- 术语使用与上下文文档保持一致
- 将文档保存到项目 `req-doc/` 目录下，文件名格式：`REQ-{YYYYMMDD}-{简短标题}.md`
